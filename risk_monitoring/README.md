# Риск-мониторинг: анализ файлов и XML-событий

Эндпоинты, формат `ai_analysis` для внешней системы и покрытие концепции «Система риск-мониторинга».

## Эндпоинты

Новые эндпоинты; существующие (`/get-ai-analysis/file` и др.) не менялись. Авторизация — как у остальных (`APIKeyMiddleware`), окружение — заголовок `X-API-Database` (`dev` / `stage` / `prod`).

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/risk-monitoring/files/analysis` | `{"ids": [1097, 1096], "push": true, "force": false, "recompute": false, "include_analysis": false}` | `202 {"task_id", "count", "status": "queued"}` |
| POST | `/risk-monitoring/xml/analysis` | `{"ids": [812345], "push": true, "force": false, "include_analysis": false}` | `202 {"task_id", "count", "status": "queued"}` |
| POST | `/risk-monitoring/contracts/analysis` | `{"ids": [26], "push": true, "use_llm": true, "analyze_documents": true, "force": false, "include_analysis": false}` | `202 {"task_id", "count", "status": "queued"}` |
| POST | `/risk-monitoring/organisations/analysis` | `{"ids": [7], "roles": ["customer", "supplier"], "period_months": 12, "use_llm": true, "include_analysis": true}` | `202 {"task_id", "count", "status": "queued"}` |
| POST | `/risk-monitoring/daily` | `{"date": "2026-10-20"}` (необязательно: `stages`, `push`, `use_llm`; `force` — только в отладке) | `202 {"task_id", "date", "status": "queued"}` |
| GET | `/risk-monitoring/daily/{date}` | — | сводка за дату (или `pipeline.status = running`); 404 — прогона не было |
| POST | `/risk-monitoring/typal-clauses/load` | `{"regions": ["34"], "dates": ["2026-10-15"], "read_files": true}` (пусто — по настройкам) | `202 {"task_id"}` |
| POST | `/risk-monitoring/typal-clauses/xml?read_files=true` | тело — XML `typalOrderClause` | `202 {"task_id", "versions"}` |
| GET | `/risk-monitoring/typal-clauses/customer/{inn}?kpp=&on=` | — | действующая редакция типового положения заказчика и его файл-положение |
| GET | `/task/{task_id}` (существующий) | — | `summary` (счётчики `done` / `skipped` / `error` / `not_found` / `pushed`) и `results` по каждому id |

- `ids` — до 500 id; повторы убираются.
- **Повторного анализа нет.** Запись с `ai_analysis.pipeline.status = completed` пропускается (`skipped: already_analyzed`). Неудачная (`failed`) берётся повторно до 3 попыток.
- `force` (анализировать заново) и `recompute` (игнорировать кэш LLM) — только при `RISK_MONITORING_DEBUG = True` в `configs/settings.py`; иначе 403.
- `analyze_files` (только `/xml/analysis`): сначала анализируются ещё не проанализированные файлы, указанные
  в XML (вложения, печатная форма) или привязанные к нему по `xml_source_id`; результаты — в `files` ответа задачи.
- Порядок редакций: если в одном запуске есть и прошлая, и новая редакция файла, прошлая анализируется первой
  (волнами). Прошлая редакция, уже заменённая новой (`superseded_by`), без `force` получает паспорт без анализа.
- `push: false` — пробный прогон: результат не пишется во внешнюю БД и возвращается в задаче вместе с `include_analysis: true`.
- Задачи идут в очередь `risk_monitoring` и обрабатываются отдельным воркером `celery_worker_rm` (`docker-compose.yml`).

Порядок для ночного прогона: сначала файлы, затем XML. Тогда событие XML получает резюме уже проанализированных файлов.

## Формат `risk_monitoring_files.ai_analysis` (паспорт документа)

`schema_version = "rm-file-1"`. Поля, которые читает паспорт документа во внешней системе:

| Поле | Содержимое |
|---|---|
| `doc_type` | `detected_type`, `type_decode`, `confidence` (0–1), `issues`, `key_indicators` |
| `readability` | `status`, `readability_score`, `main_language`, `language_confidence`, `issues`, `pages` (по разметке страниц; `null` для форматов без страниц), `text_chars`, `ocr` |
| `analyzed_at`, `model` | Время анализа, модель |
| `resume`, `confidence` | AI-заключение (5–10 предложений) и уверенность (0–1) |
| `raw_data` | Извлечённые данные с `evidence` (`fragment`, `section`, `page`, `confidence`): `document_name`, `summary`, `contract_number`, `dates`, `finances`, `organizations`, `law_references`, `procurement_subject`, `items`, `planned_timeline`, `execution_location`, `other_data`, … |
| `total_doc_risk` | Интегральный риск 0–1 = `1 − Π(1 − level × confidence)` по рискам документа |
| `risks[]` | `rule_id`, `title`, `description`, `level` (0–1), `confidence` (0–1), `law` (по закону закупки, см. «Каталог»), `evidence[]` (`fragment`, `section`, `page`, `confidence`, `quote_verified`), `verification_needed[]`, а также `category`, `kind`, `indicator`, `fz`, `law_model`, `severity`, `sources[]` (`ai_file` / `version_diff`). Один код — один риск: фрагменты одного кода объединены, потому что во внешней БД уникальность по `(file_id, rule_id)` |
| `similar_doc_ids[]` | `id` (id файла), `similarity`, `coverage`, `near_duplicate`, `exact_text_duplicate` |

Расширение по концепции (интерфейс пока не показывает, в `unknown_keys`):

| Поле | Содержимое |
|---|---|
| `passport` | `general` (имя, тип, размер, владелец, версия XML, закупка), `purpose`, `structure` (`main_sections`, `has_tables`, `has_appendices`, `appendices`), `key_conditions[]`, `semantics` (`topics`, `keywords`, `classification`), `technical_objects` (`brands`, `models`, `manufacturers`, `standards`), `assessment` (`completeness`, `structuredness`, `document_quality`, `legal_elaboration`, `competition_restriction` — 0–1), `recommendations[]`, `confidence` |
| `risk_profile` | По категориям (`DOC`, `FIN`, `PROC`, `AI` …): `count`, `max_level`, `score` |
| `risks_comparison` | Сравнение с предыдущей версией документа: `persisting`, `new`, `not_found_in_new_version`. Риск из `not_found_in_new_version` считается **снятым**; `null`, если предыдущей версии нет |
| `version_changes` | `previous_file_id`, `previous_eis_version`, `identical`, `similarity`, `stats` (абзацев добавлено / удалено / заменено), `summary`, `risk_relevant`, `changes[]` (`type`, `subject`, `section`, `before`, `after`, `impact`, `risk_effect`, `significance`) |
| `content_sha256` | Хэш содержимого файла |
| `pipeline` | `schema_version`, `catalog_version`, `stage` (`S1b`), `status` (`completed` / `failed`), `attempt`, `debug`, `previous_scope_id`, `model`, `prompt_versions`, `analyzed_at`, `result` (`no_text`), `error` |

Неудачная попытка пишет только `{"pipeline": {"status": "failed", ...}}`. Документ без текста — законченный результат: `pipeline.result = "no_text"`, `readability.status = "deny"`.

Эмбеддинги во внешнюю БД **не отправляются**: они хранятся в Postgres сервиса (`ai_document_chunks`).

| `risks[]`, `total_event_risk` | Тот же формат рисков, что у файлов; `sources`: `rule` (правила кода, уверенность 1.0) и `ai_event` (LLM) |
| `link` | Только для XML без `risk_monitoring_contract_id`: `method` (`purchase_number` / `contract_number` / `ikz` / `ikz_customer` / `none`), `risk_monitoring_contract_id`, `organisation_id`, `ambiguous`, `candidates[]`, `customer_inn`, `customer_kpp`. **PHP применяет привязку**, если `method ≠ none` и `ambiguous = false` |
| `pipeline` | Как у файлов, `stage = "S1a"`, `export_date` — дата выгрузки архива |

## Анализ закупки/контракта (`risk_monitoring_contracts.ai_analysis`)

`schema_version = "rm-contract-1"`, `pipeline.stage = "S2"`. Документы повторно **не** анализируются: берутся
сохранённые результаты файлов и XML — во внешней БД, а если их там нет, у нас. Файлы и XML закупки без результата
ни там, ни там сначала анализируются (`analyze_documents: true` по умолчанию): файлы, затем XML; счётчики — в
`documents` ответа задачи. Закупка — сводный объект и
пересчитывается при каждом запросе; если входные данные не изменились (`pipeline.input_hash`), пересчёт
пропускается (`status: unchanged`). Модель пишет только резюме (один короткий запрос; `use_llm: false` — шаблон).

| Поле | Содержимое |
|---|---|
| `passport` | Номер закупки и контракта, ИКЗ, закон, стадия (`notice` / `contract` / `execution` / `completed` / `terminated`), способ, предмет, ОКПД2, НМЦК, цена, снижение %, заявки, аванс, обеспечение, даты, заказчик, поставщик, изменение и расторжение, оплачено, `documents[]` |
| `package` | `completeness` (ожидаемые группы документов конкурентной закупки и недостающие), `consistency[]` (цена контракта и НМЦК в документах против ЕИС), `files[]`, `files_analyzed` / `files_total` |
| `registry` | Проверка поставщика в реестре 19.28 КоАП на дату контракта (два года с `date_begin`) |
| `events[]` | Лента событий XML закупки (новые первыми) |
| `risks[]` | Сводные риски в том же формате, что у файлов; `evidence[].src` — `file:<id>`, `xml:<id>`, `rule:<показатель>`, `black_list:<id>`, `eis`, `package` |
| `profile` | `score` 0–100 («шумовое ИЛИ»), `zone` (`green` < 40 ≤ `yellow` < 70 ≤ `red`), `delta` к прошлому баллу, `components` по категориям, `top_factors[]` |
| `resume` | Резюме для аналитика |

Источники рисков: файлы (только действующие редакции; риски, отклонённые аналитиком или устранённые, не учитываются,
подтверждённые весят ×1,5), события XML (по последней версии документа ЕИС), правила внешней системы
(показатель = 1 → код каталога: `pz_p5` → FIN-003, `zc_p1` → PROC-006 …), реестр 19.28 (REG-001), данные ЕИС
(одна заявка на конкурентной закупке → PROC-001, расторжение → CTR-020), согласованность (DOC-009), комплект (DOC-015),
«любимый поставщик» (BEH-006: поставщик закупки — крупнейший у заказчика за 12 месяцев, не меньше 3 контрактов и 40 %
контрактов заказчика; доля — в `customer_supplier`).
Пороги — `configs/settings.py`.

## Аналитика организаций (заказчик и поставщик)

`schema_version = "rm-org-1"`. Секции `customer` и `supplier`: `metrics` за `period_months` (12) месяцев, крупнейшие
контрагенты, `risks[]`, `score`, `zone`, `delta`, `resume`. Ключ заказчика — ИНН/КПП (все строки организации по годам
и дубли), поставщика — ИНН. Результат относится к канонической строке (`canonical_id`).

| Роль | Метрики | Риски |
|---|---|---|
| Заказчик | Закупки и суммы, доля у единственного поставщика и с одной заявкой, среднее снижение цены, демпинг, изменения, расторжения, штрафы, средний балл закупок и доля красной зоны, поставщики, HHI, доля крупнейшего, повторяющиеся риски, контракты с поставщиками из реестра 19.28 | BEH-001 (низкая конкуренция), BEH-006 («любимый поставщик»: доля контрактов у одного поставщика ≥ 40 %), BEH-005 (концентрация сумм, HHI ≥ 2500), HIST-001 (повтор риска в 3+ закупках), REG-001 |
| Поставщик | Контракты, заказчики, доля крупнейшего заказчика, расторжения, демпинг, статус СМП, записи реестра 19.28 | REG-001 (запись реестра действует сейчас), BEH-002 (расторжения, систематический демпинг) |

Поведенческие риски — только при 5 и более закупках за период. **Внешняя система пока не принимает
`ai_analysis` организаций**: результат хранится у нас (`ai_rm_results`, `kind = organisation`) и возвращается в задаче.
Когда API разрешит `risk_monitoring_organisations`, включить `ORG_PUSH_ENABLED` — запись будет «прочитать → слить
секции → записать».

## Ежедневный прогон и сводка (S0–S4)

`POST /risk-monitoring/daily {"date": D}` вызывает Laravel после загрузки ЕИС. Если до `DAILY_WATCHDOG_HOUR`
(06:00) вызова не было, Celery beat (`rm_daily_watchdog_task`) запускает прогон сам — за последнюю `exact_date`
окружения `DAILY_ENVIRONMENT`. Повторный вызов за ту же дату возвращает готовую сводку, а идущий прогон второй раз
не запускается.

| Этап | Что делает |
|---|---|
| S0 | XML архивов с `exact_date = D` (`queries/rm/daily_xml.sql`) |
| `files` | ещё не проанализированные файлы этих XML — `AIFileAnalyzer` |
| `xml` | события XML — `XmlEventAnalyzer` (с результатами файлов) |
| `contracts` | затронутые закупки — `ContractAnalyzer` без повторного анализа документов |
| `customers` | заказчики этих закупок с `monitoring = 1` — `OrgAnalyzer` (роль заказчика) |
| `summary` | сводка по заказчикам на мониторинге; текст пишет модель по готовым фактам, без модели — шаблон |

Внешняя БД — пакетно: общий кэш прогона (`risk_monitoring/run_cache.py`) запрашивает каждый XML, его предыдущую
версию, файлы событий, заказчиков карточек и привязку XML без закупки по одному запросу на шаг для всех документов
сразу (пачками по 500), а архив ЕИС скачивает один раз для анализаторов файлов и событий. Число запросов по видам —
в `pipeline.external_queries` сводки. Если за дату XML нет, в `scope.nearest_exports` — выгрузки в окне ±7 дней:
дата прогона — `exact_date` выгрузки, а не дата публикации документов.

Каждый этап сам пропускает уже проанализированное; сбой этапа отмечается `stages.<этап>.status = failed`, прогон
продолжается. Сводка хранится у нас (`ai_rm_results`, `kind = daily`, `external_id = ГГГГММДД`) — таблицы сводок во
внешней БД пока нет.

Сводка: `scope` (XML, файлы, закупки, из них на мониторинге), `stages`, `contracts` (зоны, `became_red`,
`score_jump` — рост балла ≥ `DAILY_SCORE_JUMP`, `red`), `events` (по типам, `important` — важность из
`DAILY_EVENT_IMPORTANCE` или с рисками), `customers` (баллы заказчиков), `attention` (реестр 19.28, переход в
красную зону, рост балла, важные события), `facts`, `resume`, `pipeline`.

## Типовые положения о закупке (223-ФЗ)

Источник — ЕИС, документ `typalOrderClause` (`getDocsByOrgRegionRequest`, подсистема `TYPAL_SUBSYSTEM = "TPOZ223"`,
регион — код ФНС). Ежедневно в 05:40 (Celery beat) загружаются публикации за последние `TYPAL_LOOKBACK_DAYS` дней по
регионам `TYPAL_REGIONS` (пусто — регионы заказчиков на мониторинге окружения `TYPAL_REGIONS_ENVIRONMENT`).
Миграция `010_typal_clauses.sql`.

- Каждая **версия** хранится отдельно (`rm_typal_clauses`): реестровый номер, версия, дата утверждения, дата
  применения (`useForBaseDate`), приказ об изменениях, способы закупки.
- **Заказчики** версии (`rm_typal_clause_customers`) — из `customerInfo`, с типом учреждения
  (`budgetAgencyType` → ГБУ, `autonomousAgencyType` → ГАУ).
- **Файлы** (`rm_typal_clause_files`): положения по типу учреждения, перечни, приказы. Текст — общий документ
  `ai_documents`; положение режется по пунктам (`chunker = typal_points`, номер пункта — `heading`) с эмбеддингами.
  Одинаковый файл (`contentUid`) в разных версиях читается один раз.
- Положение заказчика: `GET /risk-monitoring/typal-clauses/customer/{inn}` — редакция, действующая на дату, и файл
  для его типа учреждения. Следующий шаг — проверка рисков 223-ФЗ по пунктам положения заказчика.

## Результаты во внутренней БД (`ai_rm_results`)

Итоговый `ai_analysis` каждого файла и XML сохраняется и у нас (миграция `009_rm_results.sql`,
`python -m scripts.apply_migrations`): `env`, `kind` (`file` / `xml`), id во внешней БД, результат, статус,
признак отладки, `pushed` (записан ли во внешнюю БД) и ошибка записи. Промежуточные шаги (текст, тип, резюме,
риск-анализ) по-прежнему кэшируются в `ai_document_analysis`.

Если во внешней БД результата нет (`pipeline.status` не `completed`: прогон с `push=false`, сбой записи 5xx),
а у нас есть завершённый не отладочный результат — он дозаписывается во внешнюю БД без повторного анализа
(в ответе `source: internal`). Также из нашего хранилища берутся:
- коды рисков прошлой редакции файла (инкрементальный анализ);
- тип и резюме файлов события XML, если во внешней БД их нет.

Отладочный режим (`force`) хранилище не использует — анализ выполняется заново. Если таблицы ещё нет,
анализ работает как раньше (предупреждение в журнале).

## Контроль качества анализа файлов

- **Модели.** OCR и извлечение реквизитов — модель `get_llm()` (`M_MODEL_*`, мультимодальная).
  Паспорт, риски, сравнение редакций и события — `RM_REASONING_MODEL` (рекомендуется `prod_big_llm`;
  опционально `RM_REASONING_API_URL`, `RM_REASONING_API_KEY`). Не задана — используется `get_llm()`.
  Если сервер не принимает `guided_json`, схема передаётся в системном промпте. В `pipeline.models` пишутся обе модели.
- **Фильтр OCR** (`text_quality.py`). Циклы повторов (фрагмент ×10 и более) схлопываются.
  `bad` (≥ 30 % текста в циклах или < 200 букв) — анализ ИИ не проводится, `pipeline.result = ocr_bad`;
  `suspect` — анализируется очищенный текст, `pipeline.result = ocr_suspect`. Такой документ хранится
  с `ocr_status = suspect` и при отладочном прогоне (`force`) читается заново.
- **Чтение PDF** (`pdf_text.py`). Сначала текстовый слой PDF; OCR — только для страниц без пригодного слоя
  (сканы, `(cid:NN)`, неверная кодировка шрифта): 200 dpi, `repetition_penalty` 1,05, при цикле повторов —
  повтор с 1,15, затем распознавание половинами страницы. Номера страниц и их число берутся из PDF
  постранично (`Страница N:`), поэтому OCR для этого не нужен. Общий `FileReader` экспертизы не меняется.
- **Вид документа** (`doc_kind.py`). `print_form_*`, «Печатная форма …» или ссылка `printForm` — печатная форма любого XML ЕИС: тип берётся по тегу
  XML-источника (извещение / протокол / контракт / исполнение), модель не вызывается. Для прочих файлов
  тип по имени файла побеждает неуверенный детектор (< 0,85). В `doc_type` — `type_source` и `print_form`.
- **Допустимые коды рисков по типу документа** (`doc_kind.ALLOWED_BY_TYPE`): в обосновании НМЦК не ищутся
  бренды, в печатных формах протоколов, контрактов и исполнения риски в тексте не ищутся (их разбирает
  анализ XML). Список — в `ai_analysis.risk_scope.allowed_codes`.
- **Фильтры ответа модели**: уверенность ≥ 0,8, цитата найдена в тексте, описание не противоречит риску
  («соответствует законодательству»), DOC-002 — только с признаками товарного знака в цитате.
- **Реквизиты**: ИНН/КПП/ОГРН и номер контракта, которых нет в тексте, снимаются (`raw_data_issues`).
- **Паспорт**: из разделов убираются строки таблиц и ссылки на закон, из стандартов — всё, кроме ГОСТ/СП/ТР и т. п.
- **Предыдущая версия файла** (`file_versions.py`) — через diff XML: XML файла (`xml_source_id`, иначе XML
  с тем же `owner_number`, версией и группой, в чьих вложениях есть ссылка файла) → предыдущая версия XML
  (`xml_previous.sql`) → diff вложений: заменённый файл — его прежняя ссылка (`files_by_ref.sql`),
  печатная форма — печатная форма прошлого XML, добавленный файл — без предыдущей версии.
  Замена определяется по тому же имени или описанию, а если сменились и ссылка, и имя — по оценке
  `xml_events.replacement_score` (тип документа по имени, номер «3.», похожесть имён, позиция в списке;
  порог 0,5). В `documents.replaced` события — `matched_by` (`name` / `similar`), `score`, `before_file_name`. Если XML не
  прочитаны — запасной поиск по имени (`files_previous.sql`). Способ — в `version_changes.matched_by`.

## Ложные риски: нормы закона и типовые формулировки

- **Выжимка норм под тип документа** (`norms.py`): в запрос риск-анализа добавляется отдельным блоком перечень
  того, что установлено законом и поэтому не риск — для требований к заявке (ст. 31, 43, 44, 45 44-ФЗ,
  ПП № 2571, № 1005, СРО по ГрК, 19.28 КоАП), ТЗ (ст. 33, «или эквивалент», КТРУ), проекта контракта
  (ст. 34, 94–96, ПП № 1042), обоснования НМЦК (ст. 22), для 223-ФЗ — положение о закупке. Версия выжимки —
  часть ключа кэша риск-анализа.
- **Типовые формулировки** (`boilerplate.py`): цитата риска ищется в чанках документов других закупок
  (риск-мониторинг и экспертизы); если она почти дословно (≥ 80 % шинглов из 5 слов) встречается у
  `settings.BOILERPLATE_MIN_SOURCES` (3) разных заказчиков, риск снимается — `risk_scope.typical_dropped`.
  Своя закупка и свой заказчик не считаются. Отключение — `settings.BOILERPLATE_ENABLED = False`. Запросов к модели нет.
- **Риски событий**: коды правил (отмена, нет заявок, жалоба, уклонение, претензии, расторжение) модель не
  выставляет; к событиям закупки не ставятся коды контракта (CTR-*).

## Меньше вызовов модели

**События XML** (`xml_events.llm_decision`, `XmlEventAnalyzer`):
- служебные поля (`publishDTInEIS`, `plannedPublishDate`, `docDate` …) в diff не попадают; значимые изменения —
  `SIGNIFICANT_PATH_RE` (цены, суммы, обеспечение, сроки, требования, объект, изменение/расторжение, поставщик),
  без служебных `SERVICE_PATH_RE` (реквизиты счетов, контакты, ссылки и имена вложений);
- модель вызывается, только если правила нашли риск, событие важное (`high` / `critical`) или есть значимые
  изменения; первая версия и служебные изменения — шаблон `default_summary`. Причина — `pipeline.llm.reason`
  (`rule_risks`, `importance`, `significant_changes`, `first_version_template`, `service_changes_only`, `no_changes`);
- события одной закупки (контракта) за запуск разбираются одним запросом (`EventAnalyzer.analyze_batch`,
  до 6 событий и 30 тыс. символов); пропущенное в ответе событие разбирается отдельно.

**Печатные формы** (`printform_passport.py`): данные и паспорт — разбором меток печатной формы
(`knowledge_store.eis_printform.PrintForm`), без модели; сравнение редакций — только текстовый diff
(изменения разбирает анализ XML). Для печатной формы извещения в модель отправляются только строки объекта
закупки с признаками товарного знака (латиница, «КлериГель», кавычки, ®/™, артикулы, «марка», «эквивалент»);
нет таких строк — нет запроса. `pipeline.mode = print_form`.

**Новая редакция документа** (схожесть с прошлой ≥ 0,9, прошлая уже анализировалась той же версией промпта
и моделью): извлечённые данные, тип и паспорт — от прошлой редакции (сведения с исчезнувшими цитатами
снимаются, `raw_data_issues`); риски с сохранившимися цитатами переносятся, риски с исчезнувшими — сняты
(`risks_comparison.not_found_in_new_version`); модель ищет риски только в изменённых абзацах
(`version_diff.changed_text`, с соседними абзацами). Больше 40 тыс. символов изменений — анализ целиком.
`pipeline.mode = incremental`, `pipeline.incremental` — перенесено / найдено / доля изменений.

Сводка задачи (`GET /task/{id}` → `summary.llm`): `requests` — запросы к модели через `call_llm`, `failed`;
для файлов — `produced` / `reused_previous` по видам анализа и `modes`; для XML — `events`, `with_llm`, `reasons`.

## Перегрузка сервера моделей (504)

`llm_json.call_llm` — для всех запросов паспорта, рисков, сравнения редакций, событий и OCR страниц PDF:
потоковый ответ (`configs/llm_resilience.STREAM`, по умолчанию включён: шлюз не обрывает долгую генерацию), без
встроенных повторов SDK, свои паузы 5 → 15 → 45 с, не больше `MAX_INFLIGHT` (4) запросов
к одному серверу в процессе, предохранитель — после 3 сбоев подряд пауза 30 → 60 … 300 с.
Компонентам экспертизы (`FileReader`, `TypeDetector`, `DataExtractor`) в риск-мониторинге передаётся
клиент без повторов SDK — остаются их собственные повторы с паузами.

## Каталог рисков и событий

Каталог рисков — `rm-catalog-2`, 93 кода, полная таблица в `docs/risk_catalog.md`:
- каждому из 41 показателя внешней системы (`pz_p1 … pc_n6`) соответствует ровно один код, сами показатели не меняются;
- риски концепции без показателя — отдельные коды;
- у каждого риска две нормы: по 44-ФЗ и по 223-ФЗ.

Документ — источник истины. Из него скрипт `python -m scripts.build_risk_catalog` собирает `risk_monitoring/config/risk_catalog.json`, который читают `risk_monitoring/risk_catalog.py` и, при необходимости, PHP. Тест `test_catalog_json_matches_document` следит, чтобы JSON не отставал от документа. После правки таблицы:

```bash
python -m scripts.build_risk_catalog          # пересобрать JSON
python -m scripts.build_risk_catalog --check  # проверить, что JSON актуален
```

Промпты и JSON-схемы получают списки разрешённых кодов из `risk_catalog.py`:
- `DOCUMENT_RISK_CODES` — анализ файлов;
- `EVENT_RISK_CODES` — XML-события;
- `VERSION_RISK_CODES` — сравнение редакций.

**Поля риска, которые задаёт каталог** (во всех `risks[]`):
- `law` — норма по закону закупки: `fz_type` карточки для файлов, `fz` архива или карточки для XML. Например, «Федеральный закон № 223-ФЗ: ч. 25 ст. 3.2; …». Если закон не определён, указываются нормы обоих законов через « | ». Норма модели, если она отличается от каталожной, сохраняется в `law_model`;
- `kind` — `risk` / `violation` / `ai`;
- `indicator` — показатель внешней системы (`pz_p1` …) или `null`;
- `fz` — 44 / 223 / `null`.

Риски, неприменимые к закону закупки, отбрасываются. Например, PROC-007 (ст. 111 44-ФЗ) для 223-ФЗ.
